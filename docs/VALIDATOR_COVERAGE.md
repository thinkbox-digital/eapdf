# EA-PDF Validator Coverage Matrix

Role-mapping update (2026-10-29): Java and Python now resolve a root element's
standard role through the applicable RoleMap or RoleMapNS chain. Custom roots
mapped to Document are accepted. PDF 2.0 namespace targets must use registered
namespace dictionaries and resolve to the required standard role; malformed
mappings, cycles and unresolved roles fail. The separate EA-PDF compatibility
RoleMap requirements remain. Mapping traversal is bounded at 4,096 steps; hitting
that limit is unavailable evidence, and cannot hide a separate definite failure.

The issue #1/#2 review does not remove the pinned pdfmail namespace,
NonFullScreenPageMode or body-content-set attachment annotation requirements.
Omitted DPart End already defaults to Start. Creator and CreateDate provenance
remain unavailable without independent evidence; dates are not judged from their
relationship to Sent. CIDSet uses normal PDFBox subsetting and upstream PDF/A
validation, with no extra blanket absence rule. The cited forthcoming
ISO 19005-4 revision is not represented as an already published amendment.

See the [work log](EA_PDF_WORK_LOG.md) and [partial requirements register](improvement/requirements.json).
- Declared attachment XMP records in c/ci now receive Table 19 field checks. Native/source comparisons remain with the owning email children. Source-optional isolation does not make required Sent presence/format checks optional.
- Overall `PASS` requires completed veraPDF validation against an allowed PDF/A profile and passing EA-PDF checks. A skipped or unavailable PDF/A check produces `INCOMPLETE`, never `PASS`; PDF/A failures and errors produce `FAIL`. Text, JSON, HTML, and web summaries use this same policy.
- Collection members receive independent PDF/A and EA-PDF validation, recursively. Child failures fail the parent; unavailable checks, ambiguous source matches, and exceeded child budgets produce `INCOMPLETE`. The local `validate()` helper intentionally does not invoke Docker and leaves child PDF/A checks incomplete; the CLI and web entry points run both passes. `COLLECTION_CONTENT_TYPES` (§7.6) rejects every non-source contained file without EA-PDF identification, including ordinary PDFs, non-EA-PDF finding aids, spreadsheets and PREMIS XML, even when `/CI` is absent. The creator publishes ordinary finding-aid PDFs and XLSX indexes as external sidecars for c/ci; neither the collection nor its index PDF embeds those auxiliaries. Flat m/mi archives retain XLSX embedding. Any conforming EA-PDF collection child continues to receive recursive validation. Source assets include verified file-set members, not arbitrary files labeled Supplement.
- `SOURCE_FILE_SET` (§§9.1, 9.4) checks RF dictionaries against ISO 32000-2's paired filename/embedded-stream arrays and matching EF keys, and recognizes catalog Supplement members supported by exact source-asset XMP size/type/checksum evidence. Multiple independent Source assets do not imply a file set. Python `validate`, `validate_pdf` and `validate_one` accept an optional `source_file_sets={"primary-name": ["required-companion", ...]}` inventory to detect missing members against RF or catalog Supplement entries. Without source inventory or declarations, the conditional rule is N/A: a PDF alone cannot reveal a completely omitted, undeclared original companion.
- `XMP_UTF8` (§7.1.1) explicitly checks UTF-8 bytes and XML encoding declarations for document and object-level XMP, including PDF/A-3. Readable UTF-16/32 or legacy-encoded XML does not satisfy it. Rule 96 `STRUCTTREE_ROOT_DOCUMENT` already rejected arrays of length other than one; its text, diagnostics and positive/negative tests now state that cardinality explicitly, and the creation gate enforces it.
- Parsed PDF instructions replace raw-byte tag/text searches. Named property dictionaries, nested marked content, stream arrays, and Form XObjects are inspected. MCIDs, structure content references, object references, declared pages, parent pointers, and ParentTree entries are checked in both directions; malformed or orphan connections fail.
- Each email record is matched to an inspectable source before comparing headers, dates, sizes, counts, and attachments. Duplicate Message-IDs are not treated as unique identities. Unresolved matches produce `INCOMPLETE`, rather than using the first email. Optional metadata may be absent, but supplied values must agree with their source. MIME-encoded headers and unmodified quoted addresses are handled without conflating separate emails.
- An attached RFC 822 email counts as one attachment, not its nested files. The validator compares its original decoded MIME bytes, size, and checksum. Impossible calendar dates and invalid timezone offsets fail safely without interrupting unrelated checks.
- Default HTML report filenames include a unique identity, and batch summaries count failures separately from incomplete files.
- Required `Sent`, email-container shape, and per-email `Mail_GUID` uniqueness are checked without needing an inspectable source, including isolated profiles. Source reconstruction still limits comparisons of optional headers and attachment fidelity for MSG/PST inputs.
- Collection Core Fields are mandatory for every container schema. Folder-summary/portfolio fields are additional fields, not substitutes. Non-isolated `1c` requires a catalog `Source` associated file; `CollectionFrontMatter` does not substitute for required `FrontMatter`.
- DPart checks include PDF name types, indirect objects, parent references, nonempty arrays of child arrays, and single-page `End` restrictions. Embedded-file name-tree children and content-stream arrays are traversed.
- Page DPart diagnostics use explicit 1-based PDF page numbers, separately identify missing page links and uncovered pages, and reject links to detached content sets or ranges that exclude the page. For the historical BFO sample, the affected page is PDF page 2: both its `/DPart` link and range coverage are missing. Web reports distinguish affected page numbers from their count; the PDF itself is not repaired by validation.
- Passing automated checks is not independent EA-PDF certification. The generator's output can fail these stricter checks; generator-wide compliance remediation remains separate work. Preserve original email assets and use independent review and validation before archival acceptance.
- Attachment annotations remain required for XMP-declared attachments. A reference to the containing source email does not substitute for a native attachment annotation. Stored size, actual MD5 where supplied, complete MIME parameters, literal original filenames, unique XMP ownership, visibility and CropBox containment are checked. Owned attachment records require a positive email attachment count. This is a lower bound, not an exact inventory. Alternative representations do not satisfy native attachment annotations. Zero-byte policy omissions still require internally consistent size/checksum metadata and produce an explicit warning; omission alone does not make validation incomplete. Non-isolated collection source assets are embedded at the collection level with matching XMP descriptions.
- ISO TS 32005 declarations are parsed as RDF with the declarations namespace and exact conformance URI; a mention in a description or arbitrary XML element is not sufficient. This verifies the declaration, not every ISO TS 32005 requirement.
- Core Field checks follow `Mail_FieldName` / `Mail_FieldValue` structure references through nested standard elements to actual PDF text operators. The creator supplies these tags for generated headers by default. Older untagged layouts have a bounded English-header fallback that requires XMP-consistent values in the owning body content set; unrelated body text cannot substitute for missing header evidence. Unrecognized/localized layouts remain `INCOMPLETE`. Field tags themselves are optional, not a mandatory conformance requirement.
- General embedded-file checks include annotation-only file specifications, without incorrectly requiring catalog registration for every native attachment. `/Params/CheckSum`, when supplied, must be a PDF string containing exactly 16 binary MD5 bytes (`EMBEDDED_MD5_BINARY_FORMAT`); decoded payload size and digest are compared independently of declared parameters.
- `DPM_BODY_MEDIA_TYPE_MATCH_SOURCE` compares each owned BodyRendering content set with the matched retained source's MIME body representations. It excludes attachments, follows multipart/related roots, accepts alternative representations, and identifies encrypted-body media types. An absent optional source in isolated profiles is not a warning; genuinely ambiguous retained sources remain unverified.
- The Java creator's pre-replacement consistency check covers selected invariants only. It does not run veraPDF, replace this validator, certify source/rendering fidelity, or establish full EA-PDF/ISO TS 32005/accessibility conformance.
- Bookmark, logical-structure, folder, name-tree, and font-resource traversal reject cycles or excessive depth/size. Collection validation defaults to eight nesting levels, 256 child occurrences, and 256 MiB of child PDF bytes (`VALIDATOR_CHILD_MAX_DEPTH`, `VALIDATOR_CHILD_MAX_COUNT`, `VALIDATOR_CHILD_MAX_BYTES`). Duplicate child bytes reuse validation evidence without bypassing occurrence or byte limits.
- Web PDF validation runs separately with a time limit (`VALIDATOR_JOB_TIMEOUT`, default 600 seconds) and POSIX address-space limit (`VALIDATOR_JOB_MEMORY_MB`, default 2048 MiB). A shared two-slot admission limit and 600-second request budget cover generation plus validation. Web veraPDF runs in per-job, memory-limited Docker containers; timeout cleanup stops the named container as well as local subprocesses. Docker runs with the caller's UID/GID to read private temporary files without making email data publicly readable. See `docs/DEPLOY_WEB.md` for all limits and retention settings.
