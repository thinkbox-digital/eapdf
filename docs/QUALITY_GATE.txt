Conversion quality gate — small-format acceptance, 2026-11-02

Purpose

Check that small real emails retain their content and attachments, remain
readable, and pass the standalone Java validator including veraPDF. A valid
PDF/A result alone does not prove faithful email preservation.

Run from the repository root with Java 21, Maven and Python 3.12:

  python3 -m pip install -r tests/quality/requirements.txt
  python3 scripts/quality_release_gate.py --output output/quality-new-run

Use a NEW output directory each time. The command does not publish releases or
replace dist/. Builds use private temporary directories and are removed on
success or failure. Logs, individual Java test results, exact tested JARs,
conversion PDFs, page images and Java validation reports are retained in the
requested evidence directory. summary.json records PASS or FAIL. A failure is
a nonzero exit; missing inputs, missing baselines and missing reports fail.

What runs

1. Deliberate-loss tests verify that the independent checker detects missing
   recipients, paragraphs, attachments, original email bytes and pages, a
   changed source hash, and visible page damage. Archive tests also reject
   wrong page/attachment ownership, missing messages/folders/derivatives,
   changed dates, corrupted nested documents and invalid attached-email encoding.
2. Creator and standalone Java validator tests and executable packaging.
   Receipt, structured-diagnostic, small-input reliability, payload-fingerprint,
   PST precision-warning and attached-message encoding tests are mandatory, including hashing a
   64 MiB staged file with a 32 MiB Java heap; missing/skipped suites fail.
   The optional RealWorldInputTests class is excluded from this small gate
   because it includes large PST scans. Other skips must be explicitly listed
   with a reason in tests/quality/allowed-skips.json; unexpected skips fail.
3. Each Java tool is built again in a separate empty build directory. Creator
   CLI, creator GUI and validator JARs must match byte for byte. This establishes
   repeatability within this build environment, not across different JDKs or
   operating systems. The second build skips tests because the first ran them.
4. Five pinned real inputs are converted with bounded workers and heap: two
   EMLs, one MSG, a two-message MBOX sample, and a seven-message PST fixture
   linked under in/. Twelve top-level messages plus one attached email are
   checked. The original file hashes must match the reviewed corpus manifest.
5. Independent email/mailbox/OLE parsers check source expectations. PST facts
   come from retained libpff/libpst exports and reviewed native properties.
   MuPDF and pikepdf examine final metadata, per-message page ownership,
   searchable phrases, sources, native attachment bytes and text bounds.
   Nested email fields and its document attachment are checked separately.
   The creator's parsed Java records never generate the expectations.
   See tests/quality/provenance.txt for sources and explicit limits.
6. The standalone Java validator checks each final PDF, using bundled veraPDF
   for PDF/A. Missing, failed or incomplete validation fails the gate. The PDF
   hash is checked before and after validation and bound to the evidence.
7. Every page is rendered at 72 dpi in grayscale with the pinned MuPDF version.
   Page count and dimensions must match. More than 0.1% of pixels differing by
   over 16 grayscale levels fails. Searchable-text and attachment checks remain
   separate; raster comparison alone cannot prove content preservation. Only
   the generated-at timestamp on archive finding-aid pages is masked, using
   the small rectangle recorded in the manifest. Message dates are not masked.
   The corpus fixes the Java time zone to America/New_York so local and CI
   renders of reconstructed native dates use the same display zone.

The GitHub workflow runs this same command on Ubuntu for pull requests, main
pushes and manual requests. It retains evidence on failure as well as success.
Installing this workflow does not configure repository branch protection;
maintainers must require the Conversion quality check if merges must be blocked.
Remote GitHub execution is not established by a successful local run.

Reviewing a changed baseline

There is deliberately no update-baselines switch. Investigate the failed check,
read the original email, compare extracted text and attachments, and inspect
all candidate pages. Only then replace the relevant PNGs under
 tests/quality/visual/ and record why the visual change was accepted.
Do not change expected source facts to make a broken converter pass. Version
text in the footer can cause an intentional baseline change at a release.

The 22 reference pages were visually reviewed on 2026-11-02. They cover EML
HTML/text, MSG with Office attachments, MBOX and PST archives, long messages,
finding aids and a nested attached email. They are a small acceptance set, not
comprehensive coverage of all layouts, languages or accessibility behavior.
Expected hashes, subjects, addresses, dates and attachment identities were
checked against the original messages; selected body phrases were transcribed
from those messages. The manifest documents this limited scope.

Conversion receipts

The existing output progress.json now includes creation_receipts. Each entry
records the output path, SHA-256, byte size, creation checks, normalized-record
preservation comparison, profile, message count, source/attachment disposition,
and number of known source problems. Hashing occurs after configured signing
and the final creation check. Original source problems remain explicit.

Publication stays PENDING until the supervisor finishes publishing the output
set. On success it becomes PUBLISHED; failure/cancellation is NOT_CONFIRMED.
This is job evidence, not an independently verified receipt or signature.
A failure can leave a receipt for staged bytes that were never published.

PDF/A and full EA-PDF validation are explicitly NOT_RUN in creator receipts.
The release gate retains the separate actual validator report and final PDF
hash. It does not rewrite creator history to pretend those checks happened
inside the creator. Creator preservation checks compare normalized reader
records; they do not independently establish source completeness.

conversion_warnings records the existing human-readable warnings with message
identity at job scope, including reduced rendering and source problems. Existing
console/debug output and CLI arguments are unchanged. progress.json remains the
latest job's status; retain it alongside logs if durable historical evidence is
needed. No separate PDF sidecar-validation mode was added.

Remaining work

Expand the independently reviewed samples to more folder structures, native
properties, multilingual text, mixed writing directions, images, complex tables
and long threads. Add Windows/macOS acceptance, broader visual coverage,
accessibility review, and an explicit matrix of rule outcomes.

The PST sample exposes native fractional sent-time precision lost during
reconstruction (.446 and .773 seconds). The creator now warns about that loss;
the corpus records exact native and whole-second derivative values separately.
Passing the gate does not claim exact timestamp preservation. The PST and MBOX
containers are not embedded: the checked source messages are derivatives.
The nested message/rfc822 base64-wrapping defect found by this gate is fixed;
its bytes are now preserved under an allowed binary transfer encoding.

The subsequent architecture, streaming, structured-diagnostic and fuzzing work
from the quality review remains separate. This first phase establishes a safety
net for those changes; it is not a claim that all recommendations are finished.

Beta.6 adds structured conversion_diagnostics to progress.json while preserving
existing warnings. Tests cover identity updates, duplicate warning text across
different messages, publication handoff, typed decoding recovery and metadata
budgets. Small deterministic edge tests cover 128 invalid UTF-8 bytes, nested
attached emails, cancelled real-source reads, multilingual table text/bounds,
and repeated MSG attachment-order checks. These are targeted adverse-input
regressions, not comprehensive or coverage-guided fuzzing. MIME reconstruction
and warning reporting now have separate small classes.
