3. Required content-set and document-structure fields
All PDF/mail-1 files must:
contain at least one Content Set
each Content Set must be at least 1 page
the Content Set must not be blank
the first page of each Content Set must be referenced from at least one Outline item
have Outlines in the Document Catalog
have DPartRoot in the Document Catalog
as a consequence, every page must have a DPart entry. EA-PDF-v1
Profile-specific content rules:
PDF/mail-1{s,si} must represent exactly one email
PDF/mail-1{m,mi} must represent 2 or more emails
PDF/mail-1{m,mi} must contain a non-blank Content Set for each email
therefore PDF/mail-1{m,mi} must contain at least 2 non-blank pages. EA-PDF-v1

5. Required DPM fields and values
All EA-PDF files must define DPM for all pages, and all custom DPM keys must use prefix Mail_.
EA-PDF-v1
Intermediate-node DPM fields for email-associated nodes
Fields:
Mail_GUID — required
Mail_MessageID — optional
Rules:
Mail_GUID must match a pdfmailmeta:Mail_GUID property in XMP
if Mail_MessageID is present, it must match a pdfmailmeta:messageid in document-level XMP
if both are present, Mail_GUID takes precedence for identification. EA-PDF-v1
Profile cardinality:
PDF/mail-1{s,si} → exactly 1 intermediate node with Mail_MessageID / Mail_GUID
PDF/mail-1{m,mi} → at least 2
PDF/mail-1{c,ci} → none with Mail_MessageID or Mail_GUID. EA-PDF-v1
Leaf-node DPM fields
Required:
Mail_ContentSetType — required, type name
Supported values listed by the spec include:
AttachmentList
AttachmentRendering
Rules visible here:
AttachmentList must not occur in PDF/mail-1{c,ci} files. EA-PDF-v1
The extracted page is truncated before the full list of Mail_ContentSetType values finishes, so the specification likely defines additional supported values elsewhere. For a first validator pass, treat unknown values as allowed if the spec says “other values may be present,” but still enforce the profile-specific prohibition on AttachmentList in containers.

8. Required / optional XMP fields for source email assets
For non-isolated EA-PDF files that include source email assets, document-level XMP must include pdfmailmeta:assets as an unordered set of one or more asset descriptions.
EA-PDF-v1
Each asset description:
Filename — required, free text, case-sensitive filename
SizeInBytes — required, non-negative integer
ContentType — required, free text representing IANA media type, including parameters
NumberMessages — optional, non-negative integer
Checksum — required, MD5 as 32-character hexadecimal ASCII string. EA-PDF-v1
Common source-asset media types listed:
EML → message/rfc822
MSG → application/vnd.ms-outlook
MBOX → application/mbox
OST, PST → application/vnd.ms-outlook
NSF → application/vnd.lotus-notes EA-PDF-v1
The spec allows other IANA media types, but says generic types like application/octet-stream, application/zip, and text/plain should not be used for source email assets. That is recommendation-level, not hard failure.
EA-PDF-v1
9. Required / optional XMP fields for email headers
For PDF/mail-1{s,si,m,mi} the spec says all non-empty Core Fields for each email must be recorded as structured document-level XMP metadata. It immediately notes these cannot be strict validator “SHALL” checks without reprocessing original source email, but they can be validated for consistency with the PDF’s internal structures.

10. Required / optional XMP fields for email attachments
If any emails in the EA-PDF have attachments, the spec says attachment metadata should be recorded, but then defines the attachment containers themselves with required fields once present. For validator design, this means:
presence of attachment-XMP is recommendation-level globally
but if pdfmailmeta:attachments exists, each attachment description should be schema-validated strictly. EA-PDF-v1
Each attachment description:
Filename — required, string
SizeInBytes — required, non-negative integer
Message-ID — optional, string
Mail_GUID — required if Message-ID not present
Content-Type — required, free text media type string including parameters
CheckSum — optional, 32-character ASCII hexadecimal MD5 string. EA-PDF-v1
11. Practical validator rule split
For implementation, I would split the checks into three buckets:
Hard-fail
required XMP namespaces/prefixes
pdfmailid:version=1
pdfmailid:rev=2024
pdfmailid:conformance ∈ {s,si,m,mi,c,ci}
profile ↔ allowed PDF/A pairing
required Content Set / Outlines / DPartRoot / DPart presence
required Collection constraints for container profiles
required Collection Schema fields and subtypes
required DPM keys and cardinality
required logical-structure constraints, if logical tagging is present
required types and patterns for XMP fields that are actually present. EA-PDF-v1
Soft-fail / warning
missing dc:title["x-default"]
generic source asset media type such as application/octet-stream
absence of attachment-XMP when attachments appear to exist
absence of non-mandatory but recommended logical tags. EA-PDF-v1
Cross-consistency checks
Mail_GUID in DPM ↔ XMP
Mail_MessageID in DPM ↔ XMP
Content Sets ↔ Outlines ↔ DPart ranges
NumberAttachments ↔ embedded attachments / attachment metadata
Mail_Subtype / attachment Content-Type ↔ PDF embedded-file subtype where applicable. EA-PDF-v1
