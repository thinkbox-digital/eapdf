EA-PDF specification and extracted-rule reexamination, 2026-10-27
Refined against the PDF Association issue tracker on 2026-10-27.
Implementation decisions added on 2026-10-27; see the final section.
The original numbered findings describe the reviewed before-state. The final
section records the current decisions and supersedes conflicting earlier local
interpretations. Source quotations and upstream proposals remain unchanged.

The extracted rules are substantially more complete than the original requirements
summary, but the specification still contains contradictions and missing definitions.
The current rulebook also disagrees with some of its supporting audit records.

This review compares the pinned EA-PDF 1.0 specification, dated February 2025,
with validator_rule_text.json, the merged review records, the current specification-
author Word document, and selected checking code and bundled veraPDF predicates.
Page references below are printed specification pages; add seven for PDF page numbers.
XMP means the PDF's structured metadata. DPM means its map of pages to emails and
content sets. A content set is a consecutive group of pages with a common purpose.

This revision retains findings 1-48 and adds findings 49-52. The findings include
confirmed errors, unresolved interpretations, documentation problems and limits
on what validation can prove; they are not 52 demonstrated implementation bugs.

The numbered findings below include continuing specification problems for which the
project already has a local interpretation. Such an interpretation is a working
decision, not a correction published by the specification's authors. Findings about
code coverage are limited to the evidence stated; this was not a full runtime audit.

1. The document does not consistently distinguish requirements from explanations.
   Type: Specification conflict.
   Section 2 defines formal requirement words and says notes do not add requirements.
   Section 7.1 says it introduces no formal requirements, but section 7.1.1 says all
   metadata must use UTF-8. Other section 7 passages use must, needs, ought and is to
   for instructions with differing treatment in section 9. The extraction has had
   to make individual judgment calls. Readers need one explicit precedence rule and
   a consistent classification for every such instruction.
   Source: sections 2, 7.1 and 7.1.1, pp. 2-3 and 23-24.

2. The promise of validating every mandatory requirement from the PDF alone is too broad.
   Type: Specification conflict and evidence limit.
   Some requirements depend on knowing what was in the original email: whether a
   nonempty header was omitted, whether Raw-Sent is required, whether every original
   source file was preserved, and which original media parameters existed. A PDF
   cannot expose information that was omitted without leaving a trace. The rules
   correctly distinguish many unavailable comparisons, but the specification needs
   to distinguish internal consistency from completeness and source fidelity.
   Source: sections 6, 9 introduction, 9.4 and 9.8.3, pp. 22, 61, 66-67 and 86-88.

3. The required PDF/A-4 edition and the operational validation baseline differ.
   Type: Dependency limitation already recorded locally.
   The specification names ISO/DIS 19005-4:2024. The pinned profiles identify the
   2020 edition. Passing the operational profiles does not, by itself, prove coverage
   of every change in the cited draft. The local decision to use those profiles is
   reasonable but does not close the edition comparison. The required edition and
   relevant changes need an explicit, reproducible crosswalk.
   Source: section 4, p. 15; review question DEP-PDFA-EDITION.

4. The profile table and general PDF/A permission list do not agree cleanly.
   Type: Specification conflict.
   Table 2 prints PDF/A-4fe for the multiple-message profile. That is not one of the
   defined conformance names. The collection rows omit PDF/A-4e, while section 9.1
   permits it generally and section 7.6 describes collections as compatible with it.
   The current extraction treats the early table as descriptive. The source should
   provide one authoritative profile-by-PDF/A matrix and correct the 4fe spelling.
   Source: Table 2, pp. 8-11; sections 7.6 and 9.1, pp. 49 and 61; rules 3-4.
   Upstream: issue #10 explicitly identifies PDF/A-4e as the intended spelling.
   That report supports the typo correction; it does not settle the separate
   question about the collection rows. This is already reported, not a new discovery.
   https://github.com/pdf-association/report-an-issue/issues/10

5. PDF 1.7 collections are required to use a PDF 2.0-only viewing preference.
   Type: Confirmed specification conflict.
   Section 9.1 requires collection NonFullScreenPageMode to be UseAttachments without
   a version exception. Published ISO 32000-2 errata identify that value as PDF 2.0.
   The same EA-PDF section supplies a PDF 1.7 exception for single messages with
   attachments, but omits it for collections. Rule 44 repeats the unconditional
   collection requirement. The specification needs a PDF 1.7 collection alternative.
   Also, section 7.7.1 says NonFullScreenPageMode needs to be UseOutlines generally,
   which conflicts with the later profile-specific requirements.
   Source: sections 7.7.1 and 9.1, pp. 56 and 62; rule 44.
   External authority: https://pdf-issues.pdfa.org/32000-2-2020/clause12.html
   Upstream: issue #14 raises a related design problem: this preference controls
   leaving full-screen mode, but EA-PDF prohibits initial PageMode=FullScreen.
   The preference therefore does not choose the initial pane in a conforming file.
   Removing the requirement is the reporter's proposal, not an adopted correction.
   Retain the published check pending clarification; an ineffective setting can
   still be required. The PDF 1.7 value conflict above remains a separate problem.
   https://github.com/pdf-association/report-an-issue/issues/14

6. Collection source placement is not reconciled with the self-contained-child scenario.
   Type: Inconsistent specification explanation.
   Section 7.6 describes a preservation collection assembled from children that each
   retain their own source email. Section 9.1 nevertheless requires a Source file in
   the outer collection's own catalog. Sources inside children do not satisfy that
   direct catalog requirement. The current rules require the outer entry, and this
   generator duplicates sources there. The source should say whether that duplication
   is intentional or whether complete preservation in children is sufficient.
   Source: section 7.6 scenario 2, pp. 49-50; section 9.1, p. 62; rules 6-7.

7. Isolated profiles do not have a fully specified retained-source metadata policy.
   Type: Missing definition, acknowledged in current rules.
   The profile descriptions allow isolation to mean missing, partial, modified or
   untrustworthy originals. Section 9.8.2 limits its source-metadata requirement to
   non-isolated files, yet also mentions modified sources. It does not clearly state
   the metadata requirements for modified or partial source files retained in an
   isolated document. Rules 160-161 explicitly leave this interpretation open.
   Source: section 3.1, p. 7; section 9.8.2, p. 85; rules 1 and 160-161.

8. The standard lacks a mandatory, unambiguous link from each email to its source asset.
   Type: Interoperability and validation gap.
   An email has Mail_GUID, but Table 16 source records contain filename, size, type,
   count and checksum, without an email identifier list or an explicit link target.
   With multiple assets, repeated Message-IDs or overlapping mailbox exports, the
   PDF metadata may not determine which source owns an email. Source parsing and
   matching heuristics cannot always resolve that. The missing relationship limits
   the PDF-only validation promised by the specification.
   Source: sections 7.2 and 9.8.2-9.8.3, pp. 34-35 and 85-88; Tables 16 and 18.

9. Attachment records also lack a guaranteed link to a particular embedded stream.
   Type: Interoperability and validation gap.
   Original and stored filenames may differ; filenames need not be unique; streams
   may be shared; and attachment checksums are optional. The attachment's email
   identifier identifies its owner, not its particular PDF stream. These permitted
   combinations can leave multiple indistinguishable candidates. Rules 14 and 59
   handle ambiguity cautiously, but cannot prove a relationship the format does not
   record. A mandatory link or an explicit incomplete-validation outcome is needed.
   Source: sections 7.1.3, 7.5 and 9.3; Table 19, pp. 31-33, 43-45, 65 and 89-90.

10. Attachment ownership can be ambiguous even before locating the stream.
    Type: Missing identity rule.
    Table 19 allows an attachment to identify its email using only Message-ID.
    Distinct emails can share that value. Mail_GUID is only required when Message-ID
    is absent, so a file may follow the table and still leave ownership ambiguous.
    The table also does not explicitly say how to handle conflicting supplied IDs;
    the current rules extend GUID priority to attachment ownership. The source needs
    to define both ambiguous Message-IDs and conflicting identifiers explicitly.
    Source: Table 7, p. 70; Table 19, pp. 89-90; rules 14, 59 and 199.

11. Required email Content-Type disappears between the core-field tables.
    Type: Specification gap.
    Table 4 requires Content-Type even when blank. Table 18 does not define that
    email field. DPM body media types do not fully replace it: an email's top-level
    multipart type may differ from the types of its rendered bodies. The extraction
    classifies the Table 4 entry as creator guidance, leaving no corresponding
    mandatory email-XMP rule. The authors need to reconcile the two tables.
    Source: Table 4, p. 37; Table 18, pp. 86-88; inventory T4-Content-Type.

12. The tables disagree about message size and attachment-count presence.
    Type: Specification conflict, locally scoped rather than resolved upstream.
    Table 4 calls original message size and attachment count required. Table 18 makes
    size optional and requires the count only when there is at least one attachment.
    The current rules follow Table 18. The specification should use the same presence
    conditions everywhere, including what a missing count means.
    Source: Table 4, p. 37; Table 18, p. 88; rules 186-187.

13. Missing and unusable Sent dates have no complete preservation rule.
    Type: Specification conflict and missing definition.
    Table 4 requires Sent even when blank; Table 18 requires a valid dateTime, which
    cannot be an empty string. Normalization is allowed, but no method distinguishes
    a corrected original date from an invented fallback for an undated draft or a
    completely unusable date. Raw-Sent preserves erroneous text but does not explain
    the provenance of a replacement date. The source needs a clear missing-date
    representation and a way to identify normalized or substituted values.
    Source: Tables 4 and 18, pp. 37 and 87; rules 178-181.

14. The intended profile for an input containing no valid email is unclear.
    Type: Specification gap.
    The note under section 9.2 explicitly allows preserving an empty source or a
    source with no valid emails. Single profiles require exactly one email; multiple
    profiles require at least two; collection definitions describe one or more
    embedded EA-PDF files. The note does not explain which profile and metadata
    model represent zero successfully preserved messages without inventing an email.
    Source: section 9.2 and footnote 22, p. 63; Table 2, pp. 8-11.

15. The outer XMP property containing email records is not explicitly named.
    Type: Missing serialization definition.
    Section 9.8.3 specifies an unordered set of email containers and defines their
    fields, but does not explicitly name the enclosing property. By contrast, the
    neighboring sections explicitly name pdfmailmeta:assets and attachments.
    The implementation expects pdfmailmeta:email. That convention needs to be stated
    in the specification and the extracted rule, with a complete serialization
    example, so independent implementations choose the same property.
    Source: section 9.8.3, p. 86; rule 171; validate_eapdf.py email-container parsing.

16. Message-ID has two incompatible XMP spellings.
    Type: Specification error already handled by a local interpretation.
    Table 7 refers to pdfmailmeta:messageid. Table 18 defines Message-ID. XMP names
    are case-sensitive. The project accepts the former as a specific legacy alias,
    but independent implementations may disagree. One canonical spelling and an
    explicit compatibility policy are needed in the source.
    Source: Tables 7 and 18, pp. 70 and 87; local question SPEC-MESSAGEID-CASE.

17. In-Reply-To uses contradictory list terminology.
    Type: Specification ambiguity already handled locally.
    Table 18 calls this an unordered sequence. XMP distinguishes an unordered Bag
    from an ordered Seq. The current rule selects Bag. The source should explicitly
    name the intended container and whether order has any preservation meaning.
    Source: Table 18, p. 88; rule 194.

18. Address serialization and malformed-address handling are underdefined.
    Type: Interoperability gap already recognized locally.
    Table 18 requires ordered FOAF Agent records and a mailbox property, but does
    not provide a complete example or fully explain permissible URI serialization,
    address groups, non-Internet addresses, and invalid original values. The project
    uses local representation decisions and raw fields. Those choices should be
    identified as such and backed by examples and a defined fallback policy.
    Source: Table 18, pp. 86-88; local question REQ-FOAF-REPRESENTATION.

19. Attachment-list presence and attachment-list completeness need separate wording.
    Type: Specification ambiguity with a current local decision.
    Section 9.8.4 first recommends recording all attachments, then requires a set of
    zero or more descriptions. It does not clearly state the scope of the second
    sentence, especially for collections and emails with no attachments. Current
    rule 195 requires the property in every profile, including an empty Bag. That
    decision is explicit, but the source should separately state required property
    presence and recommended inventory completeness.
    Source: section 9.8.4, p. 89; rule 195.

20. Preserving malformed media types can conflict with mandatory valid PDF media types.
    Type: Specification conflict.
    Table 19 says attachment Content-Type must preserve the original field, including
    errors. Section 9.4 requires a valid media type in the PDF stream and agreement
    with the metadata. An invalid original type, or an unrepresentable malformed
    parameter field, may make both demands impossible simultaneously. Comparing
    malformed text honestly avoids false equality but does not resolve the format
    conflict. The specification needs a defined split between raw source text and
    the valid media type used by PDF.
    Source: section 9.4, pp. 66-67; Table 19, p. 90; rules 68-70 and 200-201.

21. The media-type reconstruction algorithm adds punctuation even without parameters.
    Type: Specification ambiguity and extraction mismatch.
    Section 9.4 unconditionally says to append a semicolon, then append the optional
    parameter string. Literal application produces application/pdf; when there are
    no parameters, rather than the ordinary bare type. Rule 70 can be read as adding
    the separator only when parameters exist. The algorithm needs to make the
    separator conditional and define absent versus empty parameter text.
    Source: section 9.4, pp. 66-67; rule 70.

22. The source-file count requirement contains contradictory words.
    Type: Specification error already handled locally.
    Section 9.4 combines only with at least one for Source entries. Other passages
    explicitly allow multiple independent source assets. The current rules use a
    lower bound of one. Removing the stray word would make that interpretation
    explicit, but the authors still need to confirm their intended cardinality.
    Source: section 9.4, p. 67; local question SPEC-AF-SOURCE-CARDINALITY.
    Upstream: issue #14 identifies the same ambiguity and considers both exactly
    one and at least one. It supplies no resolution. Keep the lower bound of one
    labelled as local policy, rather than claiming upstream agreement.
    https://github.com/pdf-association/report-an-issue/issues/14

23. The specification names the PDF collection key incorrectly.
    Type: Specification error already corrected in extracted rules.
    Sections 7.6 and 9.5 call the catalog key Collections. The actual PDF key is
    Collection. Copying the printed spelling creates an unrecognized key. The
    current rules correctly use the singular spelling; the source needs correction.
    Source: sections 7.6 and 9.5, pp. 52 and 67-68; rules 77-79.

24. Collection Size describes two different quantities.
    Type: Specification conflict already handled by local policy.
    Table 5 describes original message bytes, whereas Table 6 specifies the PDF
    collection Size subtype, which exposes embedded-file bytes. For an embedded
    EA-PDF, those are the PDF's bytes, not the original email's bytes. Current rules
    keep the prescribed subtype and flag the ambiguity. The source should define
    separate, clearly named fields if both quantities are intended.
    Source: Tables 5-6, pp. 53 and 68; rules 16 and 86.
    Upstream: issue #17 reports this same conflict and proposes a numeric field
    instead of the Size subtype. The discussion does not adopt that proposal.
    Do not change the prescribed subtype merely because the proposal exists.
    https://github.com/pdf-association/report-an-issue/issues/17

25. The collection minimum-field lists disagree, and their examples are incomplete.
    Type: Specification inconsistency.
    Table 6 requires Message-ID; Table 5 and Example 5 omit it. The two minimum lists
    can be satisfied together, so this is not an impossible requirement, but the
    example is insufficient under the later table. A single minimum list should
    govern both the prose and the example.
    Source: Tables 5-6 and Example 5, pp. 53-55 and 68; rules 16 and 86.
    Upstream: issue #17 also reports the missing Message-ID in Table 5. Its only
    comment addresses Bcc, not this discrepancy or the Size problem in finding 24.
    https://github.com/pdf-association/report-an-issue/issues/17

26. Collection field values for multi-email children have no defined meaning.
    Type: Interoperability gap.
    Collections may contain a single-message PDF, a multi-message PDF or another
    collection. The same schema requires fields such as To, Sent and Message-ID.
    The source does not define how those per-email fields should summarize a child
    containing many emails, nor when item values may be left absent. Requiring schema
    keys alone does not settle this. A clear optional-value or summary convention
    would avoid misleading collection indexes.
    Source: section 7.6, pp. 49-54; section 9.5 and Table 6, p. 68.
    Upstream distinction: Peter Wyatt explains in issue #17 that retaining Bcc was
    deliberate, so preservation can distinguish a blank field from an unrecorded
    one. A blank Bcc column is not itself a specification defect. Keep the required
    schema field; this rationale does not define multi-email summary values or
    authorize inventing recipients that were absent from the original email.
    https://github.com/pdf-association/report-an-issue/issues/17#issuecomment-3525476611

27. Table 11 requires a custom tag that the specification never defines.
    Type: Specification error already corrected by an approved local interpretation.
    The Mail_ContentSet row permits Mail_ContentField, but Table 10 defines
    Mail_Field instead. The next row excludes other defined custom tags, making
    literal application especially problematic. Rule 120 correctly identifies its
    use of Mail_Field as the approved correction. The published table still needs
    that correction.
    Source: Tables 10-11, pp. 75-76; rule 120.

28. Collection content-set parent requirements are impossible as written.
    Type: Specification conflict already handled locally.
    Table 13 requires Mail_ContentSet in every file and always beneath Mail_Message,
    while prohibiting Mail_Message in collections. The project exempts collection
    front matter from that ancestry rule. The source needs an explicit collection
    hierarchy, including reports and policy pages, not only an informal exception.
    Source: Table 13, p. 79; rules 133 and 139-140.

29. The same ancestry rule also mishandles document-wide content in noncollections.
    Type: Additional specification conflict not solved by the collection exception.
    Table 3 shows front matter and document-wide reports outside the individual
    email Document elements. When custom tagging is used, section 9.7 requires every
    content set to have Mail_ContentSet, and Table 13 puts every such element below
    Mail_Message. For a multi-email conversion report, that would assign global
    content to one email. Current rule 140 exempts collections only. The source needs
    an ancestry rule based on whether a content set belongs to an email or the whole
    document, rather than only on the file profile.
    Source: Table 3, p. 28; sections 9.2 and 9.7, pp. 64 and 76-79; rules 123 and 140.

30. Optional tagging is followed by apparently unconditional tagging requirements.
    Type: Specification ambiguity, largely handled in current rules.
    Section 9.7 makes logical structure and custom tags optional. Later text and
    Table 13 say certain elements shall occur in all files, without consistently
    repeating that condition. The rulebook generally adds the missing condition,
    which is sensible but interpretive. The source should introduce a clear block
    of requirements that apply only when logical structure or custom tags are used.
    Source: section 9.7, pp. 74-79; rules 129-139 and 205.

31. Namespace and backward-role-map applicability remain inconsistent.
    Type: Specification ambiguity and local-document disagreement.
    Section 9.7 refers to all PDF/A-4 files with logical structure while describing
    custom EA-PDF semantics. The project requires the EA-PDF namespace only when
    custom tags are used. Separately, the local decision says Table 9 compatibility
    mappings apply to tags actually used; rule 109 says to include the Table 9 map
    without stating that limitation. The source and current rule text need to agree
    on both conditions, and distinguish RoleMap from namespace-specific RoleMapNS.
    Source: section 9.7 and Table 9, pp. 74-75; rules 107 and 109; review question 3.
    Upstream: issue #21 raises both the mapping location and unused-tag questions.
    It also challenges the claimed compatibility: one global map cannot preserve
    every distinction between namespaces, including MathML. The source should
    state the limited compatibility it promises. The proposed removal of the map
    has not been adopted, so the published requirements still apply.
    Caution: the issue's quoted table reverses the first pair. The pinned Table 9
    says Artifact maps to Private; it does not say Private maps to Artifact. Keep
    the published direction in rule 109, not the reversed quotation.
    https://github.com/pdf-association/report-an-issue/issues/21

32. One required metadata comparison has no defined XMP counterpart.
    Type: Missing definition.
    Table 13 says a supplied Mail_ContentGroup ContentSetType must match DPM and
    XMP. The document-level XMP tables do not define a corresponding content-set
    type property or a link to it. The current rule acknowledges unbound XMP fields,
    but the extraction cannot manufacture the missing schema. The source should
    name the XMP property and its relationship, or limit the comparison to DPM.
    Source: Table 13, p. 79; Tables 16, 18 and 19; rule 138.

33. Nonblank requirements do not clearly distinguish pages from whole content sets.
    Type: Specification ambiguity and inconsistent rule summaries.
    Section 9.2 defines a blank page, then uses a sentence about at least one content
    set of one or more pages that shall not be blank. It should state explicitly
    whether every page must be nonblank, every set needs one nonblank page, or only
    a minimum number of nonblank sets is required. The Python check currently looks
    for a nonblank page in each set; rules 5, 51 and 52 all summarize the requirement
    as at least one nonblank set. Those are materially different claims.
    Source: section 9.2, p. 63; rules 5, 51-52; validate_eapdf.py content-set checks.

34. Attachment visibility has no mandatory fallback when an email has no body set.
    Type: Specification boundary needing clarification.
    Section 9.3 requires attachment annotations in each BodyRendering content set.
    The specification also permits draft emails without bodies and does not require
    every email to have a BodyRendering set. In that case the quantified annotation
    requirement has no applicable set. Rule 59 explicitly reports it as not
    applicable. If every declared attachment is intended to have a visible access
    point, the source needs a fallback location, such as a header or attachment-list
    set. Otherwise it should explicitly acknowledge this permitted exception.
    Source: section 3.2, p. 14; section 9.3, p. 65; rule 59.

35. Text preservation changes from mandatory to recommended between sections.
    Type: Specification conflict, handled by following section 9 locally.
    Section 7.4.1 says all original textual content must use PDF text objects.
    Section 9.3 makes that a recommendation, while requiring text objects for Core
    Fields that are rendered. PDF/A conformance alone does not prove that omitted
    source text was preserved. The source should distinguish mandatory rendered
    Core Field representation from recommended full source-text preservation.
    Source: sections 7.4.1 and 9.3, pp. 39 and 64-65; rules 9 and 58.

36. Figure 6 uses the wrong metadata identifiers.
    Type: Confirmed diagram errors.
    The diagram labels EA-PDF identification with a namespace ending /eapdf/ns/
    instead of /eapdf/ns/id/, and source/email/attachment metadata with /eapdf/meta/
    instead of /eapdf/ns/meta/. It also shows pdfmailid:part where Table 15 requires
    version and reserves part for future use. These are not interchangeable labels.
    An implementer copying the figure could create metadata the actual tables reject.
    Source: Figure 6, p. 25; Tables 14-15, p. 84. Visually verified.

37. The media-parameter and attachment examples contain substantive inconsistencies.
    Type: Example errors.
    Example 3 separates CSV parameters with a comma and uses headers=present; the
    registered CSV parameter is header and MIME parameters use semicolon separators.
    Example 4 changes between Report.doc and Report.docx, supplies a name parameter
    in the source Content-Type, then says no media parameters exist in the PDF
    stream. It also prints indirect references with the letter O instead of zero
    and labels the converted PDF stream's content as XMP. These examples need to be
    internally consistent even if they intentionally demonstrate malformed source
    email or use placeholders for omitted PDF data.
    Source: Examples 3-4, pp. 46-48.
    CSV authority: https://www.rfc-editor.org/rfc/rfc4180#section-3

38. The collection explanation reverses its illustration, and its sample repeats an object number.
    Type: Editorial and example errors.
    Section 7.6's numbered scenarios assign the shared-source and independent-source
    cases to the opposite sides from Figure 11 and the following explanation.
    Example 5 later defines object 11 a second time for the second account folder,
    although the preceding Next reference points to object 12. These can mislead
    readers about preservation ownership or produce a broken copied object graph.
    Source: section 7.6, pp. 49-51; Example 5, pp. 54-55.

39. The DPart diagram and Example 6 do not form a consistent object tree.
    Type: Confirmed diagram and example errors.
    Figure 12 reuses object 104 for front matter and a conversion report, including
    conflicting page identities. Example 6 contains 10 R instead of 10 0 R, references
    object 104 from two different parents, gives that object Parent 12, and leaves
    the conversion-report object 99 outside the shown child lists. It also places
    Metadata on a DPart, which the published correction used by current rule 57
    prohibits. The example needs rebuilding and checking against the inherited PDF
    rules; checking table coverage does not catch these object-graph errors.
    Source: Figure 12 and Example 6, pp. 69 and 71-73; rule 57. Visually verified.

40. The custom-tagging example contradicts its own tables and PDF syntax.
    Type: Confirmed example errors.
    Example 7 labels the HTML and plain-text content-set objects 103 and 104 as
    Mail_ContentGroup. Their parent comments and Mail_Subtype attributes instead
    describe Mail_ContentSet; the printed types violate Tables 11 and 12. The root
    comment says NOT ARRAY although the normative paragraph expressly permits a
    one-element array. The content example gives TJ a string instead of its required
    array operand. It also omits a worked connection between custom elements and
    the declared EA-PDF namespace. A complete, valid example would be much safer
    than expecting readers to infer corrections to these details.
    Source: Example 7, pp. 81-83; section 9.7, p. 74; Tables 11-12. Visually verified.

41. The current merged review data contradicts the active attachment-list rule.
    Type: Confirmed extracted-rule inconsistency.
    Rule 195 requires an attachments Bag in every file. However, the review data
    loaded by load_review_rules still contains the earlier local decision that
    absence alone is not a mandatory failure. Its XMP-ATTACHMENT-RECORDS inventory
    record applies only when descriptions are supplied. The Markdown question and
    current Word document have been corrected, so different generated views can
    present different answers from the same project. Update the active supporting
    records and mark the older decision as superseded rather than still current.
    Source: validator_rule_text.json rule 195;
    docs/improvement/specification-audit/validator-rule-review.json:
    XMP-ATTACHMENT-RECORDS and SPEC-ATTACHMENT-SET-PRESENCE;
    docs/improvement/specification-audit/review-questions.md question 4.

42. Several rule descriptions do not describe the individual check they label.
    Type: Confirmed extracted-rule clarity problem.
    Rules 35-36 are generic navigation-presence checks, mapped to all profile cases,
    but their descriptions mention only single emails without attachments. Rule 45
    describes DisplayDocTitle=true even though VIEWER_PREFS separately reports
    whether the preferences dictionary exists. Rule 52 describes a nonblank content
    set even though 267 checks whether the PDF has pages. Multiple rules also
    repeat the same combined description. A pass for one narrow check must not read
    as proof of the entire combined requirement. Give each check its actual scope.
    Source: rules 35-36, 45-46 and 51-52; validate_eapdf.py check_pages and
    check_catalog_rules; the rules' requirement mappings.

43. Some recommendations lose their strength in the standalone rule descriptions.
    Type: Extracted-rule presentation gap.
    For example, rule 58 says to use PDF text objects without saying that this is a
    recommendation. Rules 10-11, 60-64 and 128 have similar imperative summaries.
    The separate review data, and the Word document's strength line, retain SHOULD,

Implementation decisions and remaining author questions, 2026-10-27

The user authorized reasonable local decisions and corresponding implementation
updates. These decisions are not published corrections. Each entry answers the
related finding and preserves the question for specification-author review.

Finding 1. Question: Which text controls conflicting requirements?
  Working assumption: Use section 9 and its normative tables for file requirements,
  inherited PDF/PDF-A rules for valid representations, and published errata for
  corrections. Earlier explanations inform intent; they do not silently strengthen
  SHOULD into MUST.

Finding 2. Question: Can a PDF prove that nothing was lost?
  Working assumption: No. Separate observable internal consistency from source fidelity
  and creator evidence. Missing or ambiguous evidence must not be reported as a proved
  match.

Finding 3. Question: Which PDF/A-4 edition can be checked now?
  Working assumption: Keep the pinned 2020-edition veraPDF profiles as the operational
  baseline. Equivalence to the cited 2024 draft remains unverified; no duplicate PDF/A
  engine is invented.

Finding 4. Question: Which conformance levels are allowed?
  Working assumption: Use the section 9.1 list, including PDF/A-4e, subject to the
  actual PDF/A feature restrictions. Treat 4fe as the reported spelling error, not a new
  level.

Finding 5. Question: What should a PDF 1.7 collection use for the full-screen exit mode?
  Working assumption: Use UseOutlines for PDF 1.7 and UseAttachments for PDF 2.0. Keep
  the required preference and collection PageMode=UseAttachments. This newly authorized
  local version exception is not upstream errata.

Finding 6. Question: Can sources retained only inside children satisfy the outer collection?
  Working assumption: Keep the outer catalog Source requirement as well as independently
  preserved child sources. The creator retains both; changing preservation ownership
  needs an author decision.

Finding 7. Question: What does an isolated file promise about retained originals?
  Working assumption: Isolation does not prohibit retained source files or certify their
  completeness. Validate supplied asset records and observable links; do not require an
  invented complete-original inventory for isolated profiles.

Finding 8. Question: How should email-to-asset ambiguity be handled?
  Working assumption: Keep exact GUID priority and uniquely supported source
  associations. Report unavailable comparisons when records cannot identify one source;
  do not add an unstandardized mandatory link property.

Finding 9. Question: How should attachment-to-stream ambiguity be handled?
  Working assumption: Use independent filename, size, checksum and source evidence
  within the owning email. Equivalent candidates can prove a field value, not unique
  identity. Contradiction is proved only when all available candidates disagree.

Finding 10. Question: What if Message-ID is duplicated or conflicts with GUID?
  Working assumption: Use supplied GUID as the primary identity. Message-ID alone must
  identify one email. Ambiguity is unavailable evidence; never borrow another message's
  attachment evidence.

Finding 11. Question: Should the missing email Content-Type field be invented?
  Working assumption: Preserve the source header and rendered Core Fields where
  required. Do not invent a mandatory Table 18 property absent from that schema. DPM
  media-type and attachment Content-Type checks remain separate.

Finding 12. Question: Which size/count presence conditions control?
  Working assumption: Apply Table 18: SizeInBytes is optional, NumberAttachments is
  required when there are attachments. Keep source preservation and rendered Core Field
  obligations separate from XMP property presence.

Finding 13. Question: What date should represent an absent or invalid Sent value?
  Working assumption: Keep Sent required and correctly typed; retain Raw-Sent when
  normalization needs it. Never substitute conversion time for an unknown send time.
  Creation must surface missing required evidence rather than fabricate a valid history.

Finding 14. Question: What profile represents an input with no valid messages?
  Working assumption: Do not claim s or m conformance for zero messages. Reject an empty
  email conversion or leave diagnostics outside an EA-PDF claim. A new zero-message
  profile requires specification clarification.

Finding 15. Question: What is the email-list property?
  Working assumption: Continue using pdfmailmeta:email as an unordered Bag, as the
  existing schema interpretation and creator do. Do not introduce a competing property
  name.

Finding 16. Question: Which Message-ID spelling is accepted?
  Working assumption: Accept the recorded messageid and Message-ID forms with exact
  values. If both are supplied they must agree. Keep the creator's canonical output; do
  not normalize identifier case or punctuation.

Finding 17. Question: Is In-Reply-To ordered?
  Working assumption: Treat it as an unordered Bag of normal strings. Ordered Seq and
  Alt do not satisfy this local interpretation.

Finding 18. Question: How should addresses and malformed originals be represented?
  Working assumption: Use ordered FOAF Agent records and supported equivalent URI/text
  forms. Preserve non-SMTP or malformed originals in raw fields rather than fabricate
  mailboxes. Unhandled legal representations remain unavailable.

Finding 19. Question: Must the attachments Bag always exist?
  Working assumption: Yes, including an empty Bag. Complete original attachment
  inventory remains SHOULD. Required property presence and required supplied-record
  schema are distinct from recommended completeness.

Finding 20. Question: Can malformed original media types be silently repaired?

Finding 21. Question: Should reconstruction add an empty trailing semicolon?
  Working assumption: Append the separator only for nonempty parameters. Absent and

Finding 22. Question: Must there be exactly one source?
  Working assumption: Require at least one source for nonisolated preservation profiles;

Real-world corpus follow-up, 2026-10-27

Question: How should a sender's date with no timezone be represented?
Working assumption: A complete local date and time can be preserved in XMP Sent
without a timezone. Do not assign UTC, the computer's timezone, or a Received
header's timezone. Keep the original invalid Internet Date header in Raw-Sent.
The new mailing-list exports use ctime-style dates, for example
'Tue Mar  5 16:08:13 2019'. The creator now accepts that exact, strictly parsed
form and emits '2019-03-05T16:08:13'. A completely absent or unparseable date still
blocks creation. Collection date sorting metadata is omitted when encoding it
would invent a timezone. No rulebook relaxation is needed: XMP dateTime already
permits a missing timezone, and both validators accept that value type.

Question: What should happen when an email declares an unknown character set?
Working assumption: Preserve the source bytes and report a rendering recovery.
For the real files declaring 'windows-3839', use UTF-8 when it decodes without
error; otherwise use Windows-1252 as an explicitly reported display assumption.
This does not claim that the guessed encoding is the sender's actual encoding.
The PDF includes the conversion warning and retains the original source.

Question: Does empty RTF rendering always indicate lost content?
Working assumption: No. One real PST has a valid RTF formatting wrapper with no
visible text. Independently read its text before accepting an empty display,
retain the original RTF, and record the recovery. Do not accept an unrendered RTF
image or embedded object as an empty email body.

Question: Can a missing PST attachment payload be replaced with an empty file?
Working assumption: No. A missing payload is different from a stored zero-byte
attachment. Stop that conversion with the input path, message descriptor and
attachment position, rather than silently dropping the attachment or crashing
with a null-pointer exception.

Question: Can a valid Outlook MSG be marked compliant when original headers or
attachment evidence cannot be inspected?
Working assumption: No. Keep the result incomplete, while retaining any verified
native-property comparisons. These are limitations of the available independent
validation evidence, not proof that the generated file violates the standard.

other folders. In pst_16_2005b_May-Jul_GovernF.pst, the only count discrepancy is

Question: Does a native PST Content-ID make a named file cease to be an
attachment? Working assumption: No. The reconstructed MIME source gives each
native PST attachment a filename. Named non-body files count as attachments,
including those with Content-ID. The creator now follows the existing EML and
validator rule, so the PDF count agrees with its retained source. A Word document
