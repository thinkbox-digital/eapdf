## Proof-of-concept priorities

1. **Days 1–2: finish the email output.** Clear body and attachment sections, useful bookmarks, working attachment icons, readable text and images, and smaller files. Finish the section work already underway.
2. **Days 2–3: cover common inputs.** Demonstrate ordinary EML and MSG files, a small PST archive, HTML and plain text, common international text, inline images and ordinary attachments. Preserve original email and attachment bytes.
3. **Days 3–4: make the app easy to use.** Check the GUI's choose-input, convert, progress, error and open-output steps. Keep CLI arguments unchanged. Make the current CLI and GUI builds easy to find and run.
4. **Days 4–5: make collections useful.** Demonstrate a small folder archive with a clear finding aid, plain file lists and access through the viewer’s attachments panel.
5. **Days 5–7: polish and prepare the demo.** Fix visible problems on the agreed examples, confirm the saved PDFs with existing validators, and provide a short run guide and known limits. Use remaining time for high-impact fixes.

**Done means:** a user can start the GUI, convert the common examples, read the PDFs, follow bookmarks, open attachments and browse a small collection through the viewer’s attachments panel without help. Saved examples pass the existing applicable checks, or have a clearly stated tool limit. Build and demo files identify the same creator source.

**Keep out of this cycle:** obscure or damaged MIME/MAPI cases, large-archive stress work, new validator rules, broad standards research, and full accessibility certification. Digital signing is optional stretch work only if a suitable certificate and key are available. Gmail is a stretch demo if an authorized account is available; it will not hold up the local-file demo.
