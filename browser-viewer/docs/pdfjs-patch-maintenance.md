# Reproducing the PDF.js patch stack

Upstream PDF.js is pinned to **6.5.438**, commit
`0a4153349dc473ba950fc17941c5ca7eda43c1de`. The npm installation remains
unmodified and supplies the original rendering assets/notices. The new public
method is built from upstream source, not injected into compiled JavaScript.

`vendor/pdfjs-patches/0001-document-parts.patch` changes three existing files:
`src/core/catalog.js`, `src/core/worker.js`, `src/display/api.js`; it adds
`src/core/document_parts.js`. The patch has no EA-PDF application dependency.
`manifest.json` records the exact archive hash, relevant pristine source hashes,
upstream lockfile hash, local build/test input hashes and both generated outputs.
`vendor/pdfjs-patched/` contains the generated display/worker bundles.

Normal `npm run build` verifies the source/build-input/output hashes and copies
those generated bundles. It does not need GitHub, Python, Java, a backend, or the
upstream 931-package development toolchain. The extension is entirely local.

## Clean source reproduction

Use Node 24.19.0 and npm 11.17.0, with Git, curl and tar available:

```sh
npm run verify:pdfjs
npm run build:pdfjs
```

The second command downloads the exact upstream archive (about 100 MiB), verifies
its SHA-256, extracts into a new `/tmp` directory, checks pristine source hashes,
and runs `git apply --check` followed by `git apply`. It installs upstream's exact
package-lock with `npm ci --ignore-scripts`, skipping browser downloads, then
builds only display/worker bundles with upstream's own bundle functions. Source
tree and build products are removed afterward, including on failure. npm may
use its ordinary download cache. First reproduction needs registry/GitHub access.

With a previously downloaded archive:

```sh
npm run build:pdfjs -- --archive /absolute/path/pdfjs-source.tar.gz
```

The same SHA-256 check is mandatory. Source archive SHA-256:
`eead5ce4cdc7682a791cb5661de089f1f89b6679593f11d6240e20186ac051ae`.
An actual clean detached Git checkout of the pinned commit was also tested with
`git apply --check`; the patch does not depend on archive-specific file changes.

`build-task.mjs` appends a development task to the temporary upstream gulpfile;
it is not part of the runtime/core patch. Build version/commit are supplied from
the pin, without requiring full Git history to calculate a release number.
Upstream normally randomizes its INTERNAL_EVT build define. The task explicitly
uses the original 6.5.438 npm value, `0a475cb6-573c-46ed-869d-fa7c5839d995`, so clean
builds remain identical without rewriting output JavaScript. This is an existing
build constant, not a generated runtime credential.

Each reproduction runs the focused patch tests against the actual patched core and
133 upstream specs covering catalog, primitives, message handlers, streams, parsing,
evaluation and XML. Of these, 132 pass and one requires OffscreenCanvas unavailable
in Node (recorded pending). Patch 0002 also sets ordinary DecodeStream allocation
ceilings: 64 MiB for ordinary buffers and a 256 MiB worker allocation allowance.
The large-archive patches size cross-reference decoding from its validated layout,
reclaim private structural decoder buffers after parsing, and store cross-reference
records in sparse typed-array pages. Parsed-object caching retains 100,000
entries with constant-time circular-queue eviction; evicted objects remain retrievable, and weak references preserve the
identity of objects still used by page and structure readers. Complete archive
walks yield periodically and release processed queue records. These cache
policies do not limit the number of objects inspected.
Catalog metadata inspection permits up to
128 MiB with a scoped decoder allowance; ordinary 64 MiB buffer limits are restored
after metadata extraction, and exhaustion remains explicit. Document-part and annotation mapping each
use one page-tree scan instead of repeated page lookup. The source
tests load upstream's pinned core-js Map support because Node 24 lacks
Map.getOrInsertComputed, which is otherwise handled by upstream's legacy build.
No polyfill is added to the browser package by this test setup. The full upstream
rendering/integration test suite is not run by this narrow source command.

The default command compares regenerated bytes with the stored bundle hashes and
fails on any mismatch. It never silently updates expectations or artifacts.

## Intentional patch updates

1. Start from a fresh source tree at the pinned revision; edit only the scoped
   core/display/worker changes and export a reviewed source patch.
2. Review the patch, core tests and public TypeScript contract together. Update
   corresponding `localInputs` hashes in the patch manifest. A dependency/source
   pin change requires its own review; do not relax hash checks.
3. Run `npm run build:pdfjs -- --archive /path/to/archive --write` to deliberately
   replace generated bundles and output hashes. Review all changes.
4. Run the same command **without** `--write` from another clean temporary build;
   both output hashes must match. Then run `npm run check`, `npm test` with the
   installed Chromium path, and `npm run test:m1` in its pinned reference environment.
5. Reload the unpacked extension and reopen the viewer tab. Bundled code already
   loaded in a tab/worker does not automatically change when disk files change.

The second patch, `0002-document-assets.patch`, adds generic associated-file,
metadata and collection inspection and an opt-in DecodeStream allocation ceiling.
All patches listed in the manifest are applied and hash-checked by the reproduction command. M6 rebuilt
the current stack byte-for-byte and reran all 13 focused and 73 selected upstream
tests. The extension SBOM records the exact patch-manifest hash; build-info.json
records every shipped file hash. The full upstream rendering suite is not part
of that command.

The 0.5 viewer also packages the unmodified, hash-pinned upstream web component
bundle solely for StructTreeLayerBuilder. It does not instantiate PDFViewer,
PDFScriptingManager, or an annotation-action layer. The interpreter remains
excluded. Returned structure trees are bounded before recursive DOM construction.

Indirect attachment extraction refetches a private stream decoder for each request.
After producing detached bytes (or reporting failure), it releases that decoder's
buffer allocation. Borrowed direct streams remain intact. This avoids cumulative
attachment buffers exhausting the worker allowance and restarting whole-archive
inventories. Focused tests cover repeated exact-byte reads, failure cleanup and
retained direct streams; whole-archive verification remains separate.

## Upstream compatibility audit (2026-11-07)

Patch `0004-inspection-yield.patch` changes only cooperative scheduling in the
DPart, associated-file and page-tree traversals. A shared MessageChannel helper
replaces nested zero-delay timers at the existing traversal checkpoints. Each
call closes both ports before resolving, including when several scans yield
concurrently. This yields a task rather than a microtask and avoids timer
clamping without changing PDF.js render-task cancellation or public APIs.

This follows the scheduling rationale in upstream
[PR 22161](https://github.com/mozilla/pdf.js/pull/22161). Rendering cancellation
remains subject to PDF.js's existing zoom/rotation tradeoffs, described in
[bug 1866296](https://bugzilla.mozilla.org/show_bug.cgi?id=1866296).

The object-stream cache audit found no defect requiring a cache-policy change.
Upstream [PR 11370](https://github.com/mozilla/pdf.js/pull/11370) warns against
retaining large decoded streams and sharing mutable reader positions. Our
structural cache retains decoded object-stream backing storage under its existing
eviction thresholds; each member is parsed with a fresh substream reader.
Ordinary stream objects are excluded from the parsed-object identity cache.
Cleanup discards exclusively owned decoder buffers and refunds their allocation
once. If malformed nested stream objects can retain slices, cleanup deliberately
does not refund those bytes. That accounting is conservative and is not a measure
of total JavaScript heap usage. Worker disposal remains the final release boundary.
New source regressions cover out-of-order member reads, refetch after cleanup,
idempotent cleanup, and independent malformed stream readers surviving cleanup.
Existing tests cover cache eviction, live identity, failed extraction and limits.

Our bundled PDF.js already includes upstream's on-demand attachment retrieval
([PR 21351](https://github.com/mozilla/pdf.js/pull/21351)). The custom extraction
API remains necessary for discovered associated-file identities, per-stream byte
limits and exact bytes. Complete archive inspection is retained as an explicit
application requirement; it is not added to upstream's ordinary attachment listing.
The first-page preview and separately cancellable subject indexing remain intact.

A browser-worker microbenchmark ran six alternating trials per implementation,
with 200 yields and 512 small operations per checkpoint. Chromium 156 measured
844.9–922.9 ms with timers (median 864.5), versus 8.0–11.0 ms with MessageChannel
(median 8.5). Firefox 146.0.1 measured 811–827 ms (median 823), versus 6–13 ms
(median 9). Periodic worker tasks ran in every trial. These figures isolate
scheduling overhead; they are not archive-loading throughput measurements.

Verification included 38 focused source tests, 133 selected upstream specs
(0 failures; 1 expected Node OffscreenCanvas pending spec), and a second clean
source rebuild producing byte-identical bundles. The independent pinned Python
oracle passed all 15 tests. Firefox smoke covered standalone email and collection
loading, background cancellation and close/reopen using served packaged assets;
it did not test Firefox extension installation.

The UI regression harness was also corrected to match the existing empty-file
behavior: zero-byte files show their size without View/Download controls. The
old expectation failed with the unchanged worker as well.


The November 7 repository audit adds `npm run test:pdfjs-compat`: synthetic
classic xrefs, compressed object/xref streams, incremental `/Prev` revisions,
broken-startxref recovery and AES-256 encrypted compressed objects are opened
with both the pinned upstream library and our patched bundles. Three rounds of
out-of-order page rendering/text extraction and document cleanup must produce
identical text, metadata and pixel hashes. All five cases pass in Chromium 156.
This complements the source ownership/cursor tests; it is not the full upstream
rendering corpus or an independent security review of patch 0003.


## November 8 review

Patch 0005 backports [upstream PR 22465](https://github.com/mozilla/pdf.js/pull/22465)
(source revision 37af0b407fe4246a142f1bff9232fa1e3fc18e50): a zero-width XRef stream
must retain its previous revision without file reconstruction. The upstream
StringStream fixture is included in core.test.mjs, checking the old object offset
and both revisions. Invalid widths still fail and zero-width ranges do no work.

[PR 22471](https://github.com/mozilla/pdf.js/pull/22471) proposes removing
maxImageSize for PDF.js 7. Retain the 16-million-pixel guard on our pinned 6.x
runtime. The 64 MiB canvas area setting is a resizing policy, not an equivalent
image decode-memory cap. Before upgrading to 7, remove the unsupported option
and measure large-image decoding, worker cancellation and rendered output under
bounded workloads; do not silently treat the canvas setting as its replacement.
No 7.x upgrade is included here.

## Optional collection presentation metadata

Patch `0006-collection-presentation.patch` adds an opt-in
`getDocumentAssets({presentationOnly:true})` metadata pass. It returns collection
schema/CI fields, exact byte-string initial/name-tree keys, folders, sorting and
layout preferences. It does not replace or change the default inspection result,
register new attachment extraction locators, decode payloads or execute navigator
content. BrowserSession requests it only for Portfolio presentation. Existing
EA-PDF interpretation and frozen inspection contracts remain unchanged. The reader
bounds work and text, yields during traversal and reports malformed/partial results.
Source regressions cover typed metadata, cycles, empty initial keys and the unchanged
default API shape.


## Embedded navigation and stored folder thumbnails

Patch `0007-collection-navigation.patch` serializes a bounded `embeddedAction` on
GoToE link annotations and outline items. It preserves name-tree byte keys, parent/child
steps, annotation page/index/name targets and destination names or page arrays. It does
not fetch external root files or execute actions; the browser session resolves the path
under its existing extraction and worker budgets. Cyclic/deep paths and unavailable
references are reported. Missing range data propagates for PDF.js to retry.

Two opt-in `getDocumentAssets` requests support this presentation layer:
`embeddedTarget: {page, annotation}` resolves one FileAttachment annotation to its
inspection locator; `folderThumbnail: path` decodes only a previously discovered
folder thumbnail. Neither changes the default inspection schema. Thumbnail dimensions,
mask depth and encoded sizes are checked before decoding; the existing worker allocation
and time bounds remain active. Source tests cover exact nested target serialization,
cycles, external-root rejection, lazy RGBA decoding, unknown locators and pixel limits.
